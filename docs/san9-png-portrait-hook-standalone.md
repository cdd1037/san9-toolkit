# 《三国志 IX PK》用 DLL 注入 PNG 头像：绕过 256 色调色板的独立实验指南

本文面向不熟悉任何现有改造项目、但具备 Windows x86 DLL 注入和基础逆向经验的开发者。文中的方法不修改原版资源文件，也不要求重做游戏界面；它利用原作已经支持的 16 位高彩表面，把 PNG 量化为 RGB555 后塞回头像缓存，从而绕过原头像的 8 位索引和 256 色调色板限制。

本文可以单独使用。你需要自行准备 DLL 注入器、inline hook 实现和 PNG 解码库。

## 1. 适用版本

本文确认的目标程序是：

```text
游戏：三国志 IX 威力加强版
版本：繁体中文版 1.0.1.0
文件：San9PK.exe
大小：2,636,800 字节
SHA-256：D20794AEFF67301EC2BF8C3BECB1E9944C68C6C0588FBFD4BF04E8597F0E5028
架构：x86
首选映像基址：0x400000
```

其他版本的函数地址、序言、调用约定和资源编号可能不同。不要在没有重新分析的情况下直接使用本文 RVA。注入前应先校验完整 EXE 哈希；函数入口字节校验只能作为第二道保护。

## 2. 最小方案解决什么问题

原版头像像素是 8 位索引：每个像素保存 `0..255`，真正颜色来自 `P_Face.s9` 中选定的调色板。因此即使拦截头像文件读取并换掉索引数据，每个像素仍只能从该调色板预先定义的 256 种颜色中选择。

最小绕过方案不再提交索引像素，而是让头像缓存槽持有 16 位 RGB555：

```text
原版：8 位索引头像 + 256 色调色板 -> RGB555 控件表面 -> 16 位游戏后缓冲

改造：PNG -> BGRA32 解码 -> RGB555 量化 -> 原作头像缓存槽
                                      -> 原作控件表面 -> 16 位游戏后缓冲
```

RGB555 的每个像素直接保存 5 位红、5 位绿、5 位蓝，可表达 `32768` 种打包颜色。最终画面仍是原作的 16 位画布，并不会变成真正的 RGB888；但单张头像不再受固定 256 色表限制。

这个方案的优势是仍复用原作的：

- 头像 ID 和缓存管理；
- 界面坐标及显示/隐藏状态；
- L 头像的锚点裁剪；
- 窗口层级和最终 CPU 合成；
- 1024×768 后缓冲及原作刷新时机。

## 3. 已确认的函数入口

以下 VA 以映像基址 `0x400000` 为准。实际代码中建议始终使用“主模块加载基址 + RVA”，不要把绝对 VA 强转成函数指针。

| 功能 | VA | RVA | 已确认用途 |
| --- | ---: | ---: | --- |
| 加载 L 头像 | `0x423370` | `0x23370` | 输入头像 ID 和调色板变体，返回 L 缓存资源 ID |
| 加载 S 头像 | `0x4234E0` | `0x234E0` | 输入头像 ID 和调色板变体，返回 S 缓存资源 ID |
| 加载 T 头像 | `0x423650` | `0x23650` | 输入头像 ID 和调色板变体，返回 T 缓存资源 ID |
| 按资源 ID 取位图描述符 | `0x5BDD50` | `0x1BDD50` | 返回资源对象内嵌位图描述符的地址 |
| 初始化位图表面 | `0x5BC0F0` | `0x1BC0F0` | 释放旧内容，用指定格式、尺寸和像素重建表面 |

在该版本中，可按下面的 x86 调用约定声明最小接口：

```cpp
using LoadFace = int (__cdecl *)(int portraitId, int paletteVariant);
using GetBitmap = void* (__cdecl *)(int resourceId);
using InitializeBitmap = int (__thiscall *)(
    void* bitmap,
    const BITMAPINFOHEADER* header,
    int width,
    int height,
    const void* pixels,
    int takePixelCopy);
```

这不是公开 API。每个新版本都应在 IDA 中重新检查参数使用方式、调用者清栈方式和返回值。

## 4. 为什么选择挂钩头像加载器

建议挂钩 `load_face_large`，而不是底层 `ReadFile`、C 运行库读取函数或通用图片加载器。

原因是头像加载器已经替你完成了以下工作：

1. 根据头像 ID 选择基础版或 PK 追加资源；
2. 根据尺寸和调色板变体选择正确的八槽缓存组；
3. 查找缓存命中或挑选替换槽；
4. 必要时释放旧头像并读取新头像；
5. 返回本次实际使用的资源 ID。

hook 中先调用原函数，再重建它返回的缓存槽，能保持原作缓存状态一致。若在文件读取层直接把 PNG 字节伪装成原文件内容，后续解析器仍会按 8 位索引图和原调色板解释，不能自然得到高彩头像。

## 5. 头像缓存组和资源 ID

原作共有六组头像缓存，每组八个资源槽：

| 原生资源 | 尺寸 | 调色板变体 | 返回资源 ID | 调色板槽 |
| --- | ---: | ---: | --- | ---: |
| L | 240×240 | 0 | `1369..1376` | 316 |
| S | 64×80 | 0 | `1377..1384` | 316 |
| T | 32×40 | 0 | `1385..1392` | 316 |
| L | 240×240 | 1 | `1393..1400` | 317 |
| S | 64×80 | 1 | `1401..1408` | 317 |
| T | 32×40 | 1 | `1409..1416` | 317 |

缓存组由“尺寸 + 调色板变体”决定，不区分基础头像文件和 PK 追加头像文件。头像 ID `0..785` 来自基础头像，`786..835` 来自 PK 追加头像。

如果第一轮只想替换某个普通颜色的 L 头像，hook 条件应该同时检查：

```text
portraitId == 目标头像 ID
resourceId 位于 1369..1376
PNG 已成功解码
```

检查返回的资源 ID 比只检查 `paletteVariant == 0` 更接近最终事实，也能避免错误覆盖其他缓存组。

## 6. PNG 的准备与 RGB555 转换

L 头像的完整表面是 `240×240`。建议直接准备相同尺寸的 PNG；也可以在 DLL 初始化时统一缩放。PNG 解码后取得 8 位的 R/G/B 通道，按下面公式打包：

```cpp
static std::uint16_t PackRgb555(
    std::uint8_t red,
    std::uint8_t green,
    std::uint8_t blue) {
    return static_cast<std::uint16_t>(
        ((red >> 3) << 10) |
        ((green >> 3) << 5) |
        (blue >> 3));
}
```

对应位布局是：

```text
bit 14..10 = R5
bit  9.. 5 = G5
bit  4.. 0 = B5
bit 15      = 0
```

不要写成常见的 RGB565，也不要把红蓝通道交换。若解码库输出 BGRA，则应使用：

```cpp
rgb555 = PackRgb555(bgra[2], bgra[1], bgra[0]);
```

推荐为缓存槽构造如下 `BITMAPINFOHEADER`：

```cpp
BITMAPINFOHEADER header{};
header.biSize = sizeof(header);
header.biWidth = 240;
header.biHeight = -240;       // 自顶向下
header.biPlanes = 1;
header.biBitCount = 16;
header.biCompression = BI_RGB;
header.biSizeImage = 240 * 240 * sizeof(std::uint16_t);
```

负高度很重要：它使第一个像素行对应图像顶部。若使用正高度但不主动倒序，头像会上下颠倒。

PNG 解码可以使用 WIC、libpng、stb_image 或其他库。解码和缩放应尽量在 DLL 安装阶段完成；头像加载 hook 只做缓存槽替换，避免在频繁 UI 调用中反复访问磁盘和解码。

## 7. hook 的正确执行顺序

下面是与具体 hook 库无关的伪代码：

```cpp
int __cdecl LoadFaceLargeHook(int portraitId, int paletteVariant) {
    const int resourceId = OriginalLoadFaceLarge(
        portraitId, paletteVariant);

    if (portraitId != targetPortraitId) {
        return resourceId;
    }
    if (resourceId < 1369 || resourceId > 1376) {
        return resourceId;
    }
    if (decodedRgb555Pixels.empty()) {
        return resourceId;
    }

    void* bitmap = GetBitmapByResourceId(resourceId);
    if (bitmap != nullptr) {
        InitializeBitmap(
            bitmap,
            &rgb555Header,
            240,
            240,
            decodedRgb555Pixels.data(),
            1); // 必须复制并由原作持有
    }
    return resourceId;
}
```

核心不变量是“原函数先执行”。如果 hook 完全取代原函数而不维护它的缓存 ID、年龄和替换状态，后续访问可能拿到错误人物、覆盖错误槽，或者让缓存元数据与实际像素脱节。

该版本 `load_face_large` 的入口前六字节是：

```text
64 A1 00 00 00 00
```

一个简单 inline hook 可以保存这六字节到 trampoline，在原入口写入 5 字节相对跳转，并把余下 1 字节填充为 NOP。安装前必须逐字节匹配预期序言；还应保证 trampoline 能正确执行被搬走的完整指令，再跳回 `入口 + 6`。

不要假设任意五字节都可直接搬走，也不要在未反汇编确认时切断一条指令。成熟 hook 库应使用指令解码器计算安全覆盖长度。

## 8. 最容易导致闪退的两个问题

### 8.1 像素所有权错误

调用 `initialize_bitmap_surface` 时，最后一个参数应传 `1`，要求原作分配并保存一份像素副本。

若传 `0`，位图可能直接借用 DLL 中 `std::vector` 的数据地址。原作表面后续仍可能沿拥有像素的释放链处理该指针，造成：

- 切换人物或缓存槽时堆损坏；
- 关闭界面或退出游戏时在 ntdll 内崩溃；
- DLL 自身容器扩容、析构后出现悬空指针。

不要通过“让 vector 永不释放”掩盖所有权错误。正确做法是让表面的所有权字段和实际分配方式一致。

### 8.2 COM 释放顺序错误

使用 Windows Imaging Component 时，如果调用过 `CoInitializeEx`，所有 WIC COM 对象必须先释放，再调用 `CoUninitialize`。

错误顺序可能在 `ComPtr` 析构的 `Release` 中访问已经反初始化的 COM 环境，表现为 Runtime 初始化阶段立即访问冲突。可以把全部 WIC `ComPtr` 放入一个内部作用域：

```cpp
CoInitializeEx(...);
{
    // factory、decoder、frame、scaler、converter
    // 在这个作用域结束时全部 Release
}
CoUninitialize();
```

如果 `CoInitializeEx` 返回 `RPC_E_CHANGED_MODE`，当前线程已经用另一种 apartment 模型初始化；可以继续使用已有模型，但不能为这次调用配对执行 `CoUninitialize`。

## 9. 原作并非只有三种头像显示尺寸

原作磁盘上有三套独立头像资源：

```text
L = 240×240
S = 64×80
T = 32×40
```

但已经确认的显示范围有五种：

```text
L 完整：240×240
L 裁剪：160×180
L 裁剪：96×120
S 独立：64×80
T 独立：32×40
```

两个 L 裁剪不是另外两套图片。它们从同一张 `240×240` L 表面取源矩形，所以只要替换 L 缓存槽，原作裁剪仍会自动生效。

裁剪锚点保存在两个独立文件中：

```text
D_FacPnt.s9：786 × 2 字节，头像 ID 0..785
D_FcPtPK.s9：50 × 2 字节，头像 ID 786..835
```

每条记录依次是无符号字节 `anchorX, anchorY`。PK 文件的记录索引为 `portraitId - 786`。原作等价公式是：

```text
left = anchorX + (160 - visibleWidth) / 2
top  = anchorY + (180 - visibleHeight) / 2
```

例如赵云头像 ID `9` 的锚点为 `(38, 0)`：

```text
160×180 裁剪：(38, 0) .. (198, 180)
 96×120 裁剪：(70,30) .. (166, 150)
```

因此 L PNG 应按完整 `240×240` 画布构图，并确保人物主体在原锚点裁剪范围内。

S 和 T 则是独立保存的美术资源。它们不是原作运行时从 L 缩放或裁剪出来的；要覆盖所有出现位置，需要另外准备 `64×80` 和 `32×40` 的构图，并分别挂钩 S/T 加载器。

## 10. 透明为什么不能简单处理

RGB555 没有 alpha 通道。把 PNG 中完全透明的像素转成 `0x0000`，只是在像素缓冲中写入黑色，不会自动变成透明。

原作至少存在下面这条头像显示链：

```text
RGB555 头像缓存槽
  -> 转换/复制为控件自己的 RGB555 表面
  -> 逐行直接复制，不比较透明键
  -> 最终绘制时显式禁用色键
  -> 黑色出现在画面上
```

其中已确认的 RGB555 复制函数位于 `0x5BC580`，是逐行内存复制；常见 CachedSurfaceVisual 最终绘制入口位于 `0x5B9F50`，向底层 blit 传递透明参数 `-1`，表示不使用透明键。

原作也存在能使用色键的其他图像路径，但头像控件并不统一走同一后端。即使某处成功跳过 `0x0000`，控件底面也可能本来就是黑色，不能保证露出界面木纹。

因此，最小 RGB555 方案应明确规定：

```text
PNG 必须是完整不透明画面；alpha 通道忽略。
```

如果担心某些绘制路径把 RGB555 零值当透明键，可以在“不透明模式”下把量化得到的 `0x0000` 改为很暗的非零颜色，例如 `0x0421`。这样会牺牲精确纯黑，但可避免零值在不同路径中产生歧义。这不是透明方案。

只把 alpha 分成“完全透明/完全不透明”仍不能统一解决问题，因为真正缺少的是：透明状态必须穿过所有中间表面，并在最终容器合成时有正确的背景。

## 11. 如果目标是真正的 RGBA8888

不要直接把头像位图头从 16 bpp 改成 24 或 32 bpp，然后继续调用原作的表面复制函数。原作大量路径假定：

- 一个像素占 2 字节；
- 行步长按 16 位计算；
- 混色和色键比较基于 RGB555；
- 最终游戏后台 DIB 是 16 位。

单独改变格式描述会让后续函数用错误的像素宽度或步长读内存，轻则花屏，重则越界和崩溃。

真正的 RGBA8888 通常应作为独立覆盖层实现：在游戏 16 位后缓冲上传到 D3D11 之后，根据原作当前 UI 状态绘制额外的 RGBA 纹理。它能保留完整 24 位 RGB 和 alpha，但必须自行解决：

- 当前显示的是哪个人物和哪种头像尺寸；
- 每个界面的目标坐标；
- L 头像锚点裁剪和缩放；
- 控件可见性、切页、弹窗遮挡和 Z 顺序；
- 脏矩形提交与完整 Present 的同步；
- 窗口缩放后的逻辑坐标映射；
- S/T 独立构图。

因此，RGB555 缓存替换是“颜色更多、最大限度复用原作 UI”的简单路线；RGBA8888 覆盖是“真正透明和更高色深、但需要重建头像显示状态”的完整渲染路线。

## 12. 从单头像扩展到通用替换

单头像验证成功后，不建议继续在 hook 内添加大量 `if (portraitId == ...)`。更可维护的数据模型是：

```text
key = (portraitId, nativeSize, paletteVariant)
value = (pixelBuffer, width, height, format, transparencyPolicy)
```

DLL 安装阶段：

1. 枚举配置的头像文件；
2. 校验文件名/清单中的头像 ID 和尺寸类别；
3. 解码并生成不可变的 RGB555 像素缓冲；
4. 若任何资源失败，记录明确错误并决定整项禁用或安装失败；
5. 安装 L/S/T 三个加载器 hook。

hook 运行阶段：

1. 调用对应原加载器；
2. 用 `(portraitId, size, paletteVariant)` 查找覆盖资源；
3. 验证返回资源 ID 属于对应缓存组；
4. 用复制所有权重建该槽表面；
5. 返回原资源 ID。

像素缓冲在安装完成后应只读。若实现热重载，需要单独设计 hook 调用和资源替换之间的线程同步，不能在另一个线程直接改写正在复制的 `vector`。

## 13. 建议的实机验证矩阵

第一轮只用一张完整不透明的 `240×240` 测试 PNG：

1. 不放 PNG 启动，确认 DLL 可以无覆盖运行；
2. 放 PNG 后确认目标人物的 `240×240` L 头像被替换；
3. 检查 `160×180` 和 `96×120` 场景，确认原作锚点裁剪仍在；
4. 检查 `64×80` 和 `32×40` 场景仍显示原作 S/T，确认测试边界；
5. 检查调色板变体 1 场景是否仍显示原图；
6. 快速切换多个武将，迫使八槽缓存发生替换；
7. 重复打开和关闭武将情报、列表、对话框等头像界面；
8. 读档、返回标题和退出游戏，检查释放阶段；
9. 用调试器区分 hook 安装失败、PNG 解码失败、游戏堆损坏和 COM 释放崩溃。

至少完整测试一次缓存回绕和退出流程后，才能说明内存所有权基本正确。单张成功截图只能证明一个显示入口命中，不能证明所有头像场景已经覆盖。

## 14. 最小完成标准

对于“绕过头像调色板”的第一阶段，可以把完成标准限定为：

- 指定版本校验通过后才安装 hook；
- 一张指定 ID 的 L PNG 能以 RGB555 显示；
- `240×240`、`160×180`、`96×120` 三种 L 显示保持原作裁剪；
- PNG 使用完整不透明背景，透明暂不支持；
- 缓存反复替换及游戏退出不发生堆损坏；
- S/T 和调色板变体 1 明确标为未覆盖，而不是误称“所有头像已替换”。

达到这一步，就已经实质绕过了原头像的 256 色调色板。之后再决定是补齐 S/T 的 RGB555 替换，还是投入成本实现真正的 D3D11 RGBA 覆盖层。

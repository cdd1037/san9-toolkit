# 头像调色板绕过实验

本文记录繁体中文版《三国志 IX 威力加强版》1.0.1.0 中，使用 Runtime DLL 把 PNG 头像接入原作头像控件的最小可复现实验。目标不是修改 `P_Face.s9`，也不是扩充索引图的调色板，而是在原作完成头像缓存选择后，将该缓存槽改为 16 位 RGB555 表面。

当前原型只验证赵云头像 ID `9`、调色板变体 `0` 的 L 头像。它是研究性入口，不是完整的用户功能；PNG 的透明通道目前被忽略。

## 1. 目标和不变量

原作头像文件保存 8 位索引像素。每个像素只能引用当前 `P_Face.s9` 调色板中的 256 个条目，因此直接替换索引字节仍然受 256 色限制。

本实验绕过的正是这一步：

```text
原作：8 位索引像素 + P_Face 调色板 -> RGB555 中间/目标表面
实验：PNG BGRA -> RGB555 像素 -> 原作头像缓存槽 -> 原作控件与最终合成
```

保持不变的部分包括：

- 头像 ID、缓存槽选择和缓存命中逻辑；
- 原作 L 头像的完整显示及两种锚点裁剪；
- 原作控件布局、生命周期和 16 位后台画布；
- 最终由 Toolkit 既有 D3D11 presenter 放大整个 1024×768 后缓冲的流程。

因此，这个方案提高的是头像源像素的颜色表达能力，而不是把整个游戏改成 24/32 位渲染。RGB555 有 `2^15 = 32768` 个可能颜色；原索引头像在选定调色板下最多使用 256 个预定义颜色。

## 2. 版本和关键入口

以下地址只适用于 `San9PK.exe` 繁中 PK 1.0.1.0：

| 入口 | VA | RVA | 用途 |
| --- | ---: | ---: | --- |
| `load_face_large` | `0x423370` | `0x23370` | 选择/加载 L 头像缓存槽，返回资源 ID |
| `get_loaded_resource_by_id` | `0x5BDD50` | `0x1BDD50` | 取得资源对象内的位图描述符 |
| `initialize_bitmap_surface` | `0x5BC0F0` | `0x1BC0F0` | 释放旧像素并按给定头、尺寸和像素建立表面 |

实验分支 `codex/portrait-palette-bypass` 中的原型在 `load_face_large` 函数入口安装 trampoline，先调用原函数，再检查头像 ID、调色板变体对应的资源槽，最后重建该槽的位图。主分支只保留本研究记录，不包含头像替换产品代码。

挂钩前会核对入口最初六字节 `64 A1 00 00 00 00`。这只是对目标版本和可安全覆盖指令边界的局部校验，不能替代完整 EXE 版本校验；迁移到其他版本时必须重新定位函数、确认 ABI 和指令边界，不能照抄 RVA。

## 3. 六组头像缓存

原作把尺寸和调色板变体分成六个独立缓存组，每组八槽：

| 尺寸 | 变体 | 资源 ID | 调色板槽 |
| --- | ---: | --- | ---: |
| L，240×240 | 0 | `1369..1376` | 316 |
| S，64×80 | 0 | `1377..1384` | 316 |
| T，32×40 | 0 | `1385..1392` | 316 |
| L，240×240 | 1 | `1393..1400` | 317 |
| S，64×80 | 1 | `1401..1408` | 317 |
| T，32×40 | 1 | `1409..1416` | 317 |

L/S/T 是三套独立美术资源，不是运行时从 L 自动缩放得到。当前原型只挂钩 L 加载器，并只接受调色板变体 0 返回的 `1369..1376`，所以：

- L 的 `240×240` 完整头像会被替换；
- 从同一 L 表面裁出的 `160×180` 和 `96×120` 也会被替换；
- 独立的 S `64×80` 和 T `32×40` 不会被替换；
- 调色板变体 1 不会被替换。

若要覆盖所有头像出现位置，应分别处理 `load_face_small (0x4234E0)` 和 `load_face_tiny (0x423650)`，并为 S/T 准备对应构图的资源。不要把 L 的自动缩放当成完整方案，因为原作三套图的构图并不等价。

## 4. L 头像裁剪必须保留

L 头像有三种已确认的显示范围：完整 `240×240`、锚点裁剪 `160×180`、锚点裁剪 `96×120`。后两者都引用同一张 L 表面；替换缓存槽后不应另行修改裁剪函数。

裁剪锚点来自：

- `D_FacPnt.s9`：786 条，每条两个无符号字节，覆盖头像 ID `0..785`；
- `D_FcPtPK.s9`：50 条，覆盖 ID `786..835`，索引为 `portrait_id - 786`。

每条记录是 `(anchor_x, anchor_y)`。原作等价裁剪公式为：

```text
left = anchor_x + (160 - visible_width) / 2
top  = anchor_y + (180 - visible_height) / 2
```

头像 ID `9` 的锚点为 `(38, 0)`，所以 `160×180` 源矩形是 `(38,0)..(198,180)`，`96×120` 源矩形是 `(70,30)..(166,150)`。PNG 应按完整 L 画布 `240×240` 构图，而不是只提供某个裁剪后的区域。

## 5. PNG 到 RGB555

原型使用 Windows Imaging Component：

1. 解码 PNG 第一帧；
2. 用 Fant 插值缩放到 `240×240`；
3. 转为 `GUID_WICPixelFormat32bppBGRA`；
4. 逐像素量化到 RGB555。

量化公式为：

```text
rgb555 = ((red >> 3) << 10) | ((green >> 3) << 5) | (blue >> 3)
```

位图头使用 16 bpp、`BI_RGB`、负高度 `-240`，保持自顶向下的行序。传给 `initialize_bitmap_surface` 时，最后一个参数必须为 `1`，让原作分配并持有像素副本。

这是重要的所有权不变量。传 `0` 会让表面借用 DLL 中 `std::vector` 的地址，但后续释放链仍可能按拥有像素处理，最终造成堆损坏或退出/切换界面时崩溃。

WIC 的 COM 对象也必须在 `CoUninitialize` 之前析构。原型用内部作用域保证所有 `ComPtr` 先释放；反过来的顺序曾在 Runtime 初始化期间触发访问冲突。

当前 `PackOpaqueRgb555` 会把量化结果 `0x0000` 改为接近黑色的 `0x0421`。原因是部分原作高彩绘制路径可能把零当作透明键；这项处理只用于“不允许透明”的原型，代价是纯黑不能逐位保真。

## 6. 为什么透明像素会变黑

RGB555 本身没有 alpha。把 PNG 中 `A=0` 的像素写成 `0x0000`，不等于透明语义能贯穿原作所有头像控件。

已确认的一条常用链路是：

```text
头像缓存槽
  -> convert_surface_palette (0x5BC210)
  -> copy_rgb555_surface_rows (0x5BC580)
  -> 控件自己的 RGB555 表面
  -> draw_unkeyed_cached_surface_visual (0x5B9F50)
```

其中 `copy_rgb555_surface_rows` 逐行复制像素，不比较透明键；基础 CachedSurfaceVisual 最终绘制时又把透明参数 `-1` 传给 blit，明确禁用色键。因此 `0x0000` 会成为普通黑色。即使在另一条支持键色的路径上跳过黑色，控件下面也可能只是黑色底面，并不保证能露出期望的木纹或窗口背景。

所以当前最小方案的输入约束是：PNG 必须提供完整不透明背景，alpha 被忽略。只支持“全透明/全不透明”也不能消除上述问题，因为缺失的不是 alpha 阈值算法，而是透明信息在中间表面和各容器合成过程中的一致传递。

要统一支持透明头像，至少需要选择并验证一种新的架构：

- 在所有相关头像控件最终合成前保留蒙版，并逐个处理容器底面；或
- 在 D3D11 呈现阶段叠加 RGBA8888 头像，同时复现原作控件的坐标、裁剪、层级、脏区、可见性和生命周期。

后一种方案能保留真正的 alpha 和 24 位 RGB，但它不是“把 RGB555 改成 RGB888”这么简单。原作后台画布及大量中间表面仍是 16 位；若只把某个描述符声明成 24/32 位，既有复制和混合函数会按错误的步长、像素宽度或格式读取内存。

## 7. 当前原型的资源约定

Runtime 从 Toolkit 配置文件所在目录寻找：

```text
data/portraits/large/9.png
```

文件不存在时跳过该实验，不阻止 Runtime 安装；解码失败或 hook 安装失败时 Runtime 初始化失败。原型把任意输入尺寸缩放为 `240×240`，但为了可控构图，建议直接提供 `240×240` PNG。

当前安装入口在 `runtime.cpp` 的必要 hook 初始化链中。若继续扩展，应该先把“头像 ID、尺寸、调色板变体、文件路径、透明策略”建模为显式配置和资源状态，再增加 S/T 或更多人物；不要继续复制硬编码分支。

## 8. 编译与验证

在 Toolkit 项目根目录中，且 Visual Studio C++ 桌面工具链和 Windows SDK 可用时，可运行：

```powershell
./build.ps1
./test.ps1
```

只修改 Runtime 时也可单独构建 `San9Toolkit.Runtime.vcxproj` 的 `Release|Win32`。项目需链接 `ole32.lib` 和 `windowscodecs.lib`。

建议按以下顺序由测试者实机验收：

1. 不放 PNG，确认 Toolkit 与游戏仍能正常启动；
2. 放置一张完整不透明的 `240×240` 测试图，确认头像 ID 9 的 L 全图出现；
3. 分别检查 `160×180` 和 `96×120` 场景，确认仍使用原作锚点裁剪；
4. 检查 S/T 场景仍显示原作独立资源，避免误报为“所有头像已替换”；
5. 反复打开、关闭和切换人物界面，观察缓存替换与表面释放是否稳定；
6. 退出游戏，确认没有堆损坏或 Runtime 卸载阶段崩溃。

不要用单张界面截图推断所有头像控件都走同一绘制后端。当前已确认存在“复制为控件自有表面”和“直接绑定源资源描述符”等不同路径。

## 9. 已知边界

- 只支持指定 EXE 版本，地址和入口字节不可跨版本复用；
- 只替换头像 ID 9、L、调色板变体 0；
- alpha 被忽略，只支持完整不透明图；
- 颜色仍会量化到 RGB555，不是 RGB888/RGBA8888；
- S/T 需要独立资源与独立加载器 hook；
- 尚未穷举所有头像容器和所有场景生命周期；
- 未实现运行时配置、热重载、错误 UI 或多头像资源管理。
